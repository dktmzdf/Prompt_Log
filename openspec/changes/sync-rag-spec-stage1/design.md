# Design

## Context

동기와 범위는 [proposal.md](proposal.md)를 본다. 문서 편집 방식을 정하는 현재 상태는 셋이다.

1. 1단계 상세 설계 `docs/rag-store-design.md`가 이미 있다. §3 표가 명세와 어긋나는 다섯
   곳을 기록했고, 상단 안내가 "명세보다 이 문서가 우선한다"고 선언한다.
2. 구현이 그 설계에서 한 번 더 움직였다. 스키마 버전 2(`turn.content_hash`,
   `ix_se_event`), `ON CONFLICT DO UPDATE` 적재, `--reindex`, 공유 이벤트 지문 재계산은
   상세 설계 문서에도 없다. 근거는 아카이브된 두 change의 `design.md`와 코드다.
3. 명세에는 행 번호 참조가 여럿 있고(`assemble.py:139-142`, `adapters/claude.py:22-24`,
   `adapters/codex.py:127`), 상세 설계 문서는 같은 규칙을 다른 번호(`:136-149`)로 가리킨다.
   번호가 이미 서로 어긋나 있다.

## Goals / Non-Goals

**Goals:**

- 명세만 읽는 사람이 틀린 설계를 따르지 않는다.
- 같은 사실을 두 문서에 길게 적지 않아서, 다음 번에 또 어긋나지 않는다.

**Non-Goals:**

- 명세를 상세 설계 문서의 사본으로 만드는 것. 식별자 형식 전체, 스키마 DDL, 측정표는
  상세 문서의 몫이다.

## Decisions

### 1. 명세는 결정과 이유를 한두 문단으로 쓰고, 상세는 링크한다

§3.1~3.3은 "무엇으로 바뀌었는가"와 "왜"만 적고, 형식 전체와 측정은
`rag-store-design.md`의 해당 절로 연결한다.

- 대안 A — 상세 내용을 명세에 옮겨 적는다: 명세 한 곳만 읽으면 되지만, 같은 표가 두
  곳에 생겨 다음 구현 때 다시 어긋난다. 지금의 문제가 바로 이것이다.
- 대안 B — 그대로 두고 "상세 문서가 우선한다" 안내에 기댄다: 비용이 없지만 명세 본문이
  틀린 채로 남아 2단계 change가 틀린 전제로 시작할 수 있다.
- 선택 — 본문을 맞추고 링크한다. 명세는 개요와 확정 결정의 자리로 남는다.

### 2. 행 번호 참조는 함수·파일 이름으로 바꾼다

고치는 줄에 있는 `assemble.py:139-142` 같은 번호는 `assemble()`의 턴 경계 루프처럼 이름으로
바꾼다. 번호는 코드가 한 줄만 바뀌어도 틀리고, 이미 두 문서가 서로 다른 번호를 쓴다.
고치지 않는 줄의 번호는 이번 범위가 아니라서 건드리지 않는다.

### 3. 뒤집힌 제안은 "무엇이 왜 바뀌었는지" 한 줄만 남긴다

원래 제안(`sha256(session_id + source_id)` 등)을 본문에 취소선으로 남기지 않는다. 변경
이유는 `rag-store-design.md` §3 표와 아카이브된 design이 이미 갖고 있다. 명세는 현재
설계만 말하고, 이력이 필요하면 그쪽으로 가게 한다.

### 4. 확인되지 않은 내용은 쓰지 않는다

각 수정은 코드, 테스트, 아카이브된 design 중 하나로 확인한 사실만 담는다. 2단계의 외래키
금지는 코드를 읽고 추론한 것이라 "`turn`이 매 턴 지웠다 다시 쓰이므로 외래키를 걸면
cascade가 임베딩을 지울 수 있다"는 이유와 함께 쓰고, 2단계 설계 때 확정한다고 표시한다.

## Risks / Trade-offs

- **[상세 문서와의 새 불일치]** 명세 문장을 고치다 상세 문서와 다르게 쓸 수 있다. →
  수정 뒤 두 문서의 같은 주제를 나란히 대조하는 태스크를 둔다.
- **[행 번호를 이름으로 바꾸면 찾기가 번거롭다]** 이름은 `grep`으로 바로 찾을 수 있어서
  번호보다 낫다. 문제가 되지 않는다.
- **[2단계 설계를 미리 정해 버릴 위험]** 외래키 금지와 증분 키는 2단계의 결정이다. →
  "1단계가 만드는 제약"으로만 적고 해결 방법은 2단계 몫으로 둔다.

## Migration Plan

문서 한 파일이라 배포 단계가 없다. 되돌리려면 `git revert`로 충분하다.

## 보류된 개선

구현 중 발견했지만 멈출 기준에 해당하지 않아 미룬 문제를 여기 기록한다. 항목 형식:
무엇 / 왜 미뤘나 / 고칠 방향 / 발견 시점.

### 1. `rag-store-design.md` §4가 Claude의 `claude:line:` 폴백 형식을 빠뜨렸다

- **무엇**: §4의 식별자 형식 목록에는 `claude:uuid`, `codex:item`, `codex:line` 세 가지만
  있다. 코드에는 `uuid`가 없는 Claude 메타 행(`ai-title`, `mode` 등)이 쓰는
  `claude:line:{session_id}:{_line_no}`가 더 있다(`adapters/claude.py`의 `row_prefix()`).
  아카이브된 `add-raw-log-store` design 결정 2의 목록도 같다. `rag-spec.md` §3.1에는 이
  형식을 코드대로 적었으므로 두 문서가 이 한 곳에서 다르다.
- **왜 미뤘나**: 상세 설계 문서 수정은 이 change의 Non-goal이다.
- **고칠 방향**: §4 목록에 `claude:line:{session_id}:{line_no}#{kind}` 한 줄을 더하고
  "파일 스코프, uuid 없는 메타 행 전용"이라고 쓴다.
- **발견**: 그룹 2, 태스크 2.1 (`claude:line` 문자열이 어떤 `.md`에도 없음을 확인)

### 2. `skills/prompt-log/SKILL.md`가 아직 Python 3.10 이상이라고 적고 있다

- **무엇**: 33행이 "Python 3.10 이상을 사용한다"라고 쓴다. 정책은 3.11 이상이다
  (`AGENTS.md` 2항, `README.md` 108행). `rag-spec.md` §5의 반영 위치 표에는 이 파일이
  없어서 정책 변경 때 빠졌다.
- **왜 미뤘나**: 이 change는 `docs/rag-spec.md` 한 파일만 고친다. 스킬 문서는 범위 밖이다.
- **고칠 방향**: 33행을 3.11 이상으로 바꾸고, 필요하면 §5 표에 이 파일을 한 줄 추가한다.
- **발견**: 그룹 3, 태스크 3.3 (저장소 전체에서 `3.10`을 검색)

### 3. `rag-store-design.md`가 구현 이후 상태를 반영하지 않는다

- **무엇**: 코드와 `rag-spec.md`를 기준으로 낡은 곳이 다섯 군데 있다.
  - §5 스키마: `turn`에 `content_hash`가 없고 `ix_se_event`·`user_version`이 없다(현재 v2).
    `session_key` 주석은 "session_id 원문"인데 코드는 `session_id`, 없으면 파일 stem이다
    (`store.py`의 `session_key_of()`). 스키마에 `raw_blob`이 있으나 구현되지 않았다.
  - §6 마지막 단락: "새 줄만 읽어 `raw_line`에 INSERT하므로 세션이 길어져도 매 턴 비용이
    일정하다"고 쓴다. DB 쓰기는 새 줄만이지만 `ingest_lines()`는 매번 파일 전체를 읽고
    색인은 세션 전체를 다시 쓴다. 9.0MB 세션을 다시 export하면 색인 약 160ms, 원본 적재
    약 12ms였다. 세션 길이에 비례한다.
  - §7: "`--selftest` 33건"이라고 쓴다. 지금은 105건이다.
  - §8: "`--reindex` 경로 … 1단계에 포함해야 한다"가 미결로 남아 있다. 구현됐다.
  - 상단 안내 "명세보다 이 문서가 우선한다": 명세를 맞춘 뒤에는 절반만 맞다.
- **왜 미뤘나**: 상세 설계 문서 수정은 이 change의 Non-goal이다.
- **고칠 방향**: §5에 v2 변경과 구현 상태(어느 표가 아직 없는지)를 표시하고, §6의 비용
  문장을 실제대로 고치고, §7의 건수를 빼거나 갱신하고, §8의 `--reindex` 행을 닫고, 상단
  안내를 "명세와 다르면 코드가 기준"처럼 바꾼다.
- **발견**: 그룹 4, 태스크 4.1 (두 문서를 같은 주제별로 대조)
