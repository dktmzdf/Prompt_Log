# Design

## Context

동기와 실측은 [proposal.md](proposal.md) Why를 본다. 설계를 제약하는 현재 상태는 다섯이다.

1. 청크의 재료는 `event` 표다. `turn_event_rows(conn, key, turn_no)`가 한 턴의 이벤트를
   `session_event.seq` 순으로 `(source_id, kind, ts, text, tool_name, status, payload)`
   모양으로 돌려준다. 프롬프트·답변은 `text`에, 도구 결과는 `text`에, 도구 인자는
   `payload`의 `input`에 들어 있다. 1단계에서 지문이 "`event` 표가 말하는 턴 내용"의
   해시로 정해졌으므로, 청크도 같은 표에서 만들어야 지문과 어긋나지 않는다.
2. `turn`과 `session_event` 행은 export마다 세션 단위로 지워졌다 다시 쓰이고
   `foreign_keys`는 켜져 있다. 청크나 임베딩이 이 표를 외래키로 참조하면 삭제 때 막히거나
   같이 지워진다(rag-spec §4 2단계, 코드를 읽고 추론한 것이며 재현하지 않았다).
3. `turn.content_hash`는 재색인해도 바뀌지 않는다(1단계 `add-turn-content-hash`). 다만
   도구 결과까지 포함해 계산하므로, 청크에 들어가지 않는 도구 결과가 붙어도 바뀐다.
4. Stop 훅 타임아웃은 10초(`hooks/hooks.json`)이고 리포트 경로는 표준 라이브러리만 쓴다
   (README, AGENTS.md 2항). 임베딩 의존성이 이 경로에 들어오면 안 된다.
5. `text.py`의 `summarize_tool(name, inp)`가 이미 있다. 로그에 있는 필드(Bash의 `description`,
   파일 경로, URL, 검색 패턴 등)에서 한 줄을 꺼내며 생성하지 않는다.

확인한 모델 사양(Hugging Face 모델 카드, 2026-10-06 조회):

| | `BAAI/bge-m3` | `intfloat/multilingual-e5-base` |
|---|---|---|
| 차원 | 1024 | 768 |
| 최대 입력 | 8192토큰 | 512토큰 (초과분 절단) |
| 풀링 | CLS (`1_Pooling/config.json`) | 평균 (`1_Pooling/config.json`) |
| 정규화 | 있음 (`modules.json`의 `Normalize`) | 있음 (`modules.json`의 `Normalize`) |
| 접두어 | 없음 | 질문 `query: `, 문서 `passage: ` |
| ONNX (Xenova 변환본) | int8 568MB, fp16 1.13GB, fp32 약 2.3GB | int8 278MB, fp16 555MB, fp32 1.11GB |

## Goals / Non-Goals

**Goals:**

- 청크와 임베딩이 모두 원본에서 재생성되는 파생물이다. 스키마나 청크 규칙을 잘못 잡아도
  원본이 남아 있으면 복구된다.
- 두 모델을 같은 청크와 같은 질문으로 비교해 모델 차이만 드러나게 한다.
- 임베딩은 비싸므로 내용이 같으면 다시 계산하지 않고, 중간에 멈춰도 이어서 한다.

**Non-Goals:**

- 검색 모듈. 비교용 점곱 순위만 쓰고, 검색 설계(필터 해석, FTS5, RRF)는 3단계가 한다.
- 청크 규칙의 최적화. 한 가지 규칙으로 시작하고, 비교 결과를 본 뒤 바꾼다. 규칙이 바뀌어도
  `profile` 열이 전체 재생성을 보장하므로 바꾸는 비용은 낮다.

## Decisions

### 1. 청크는 모델과 무관한 하나의 규칙으로 만든다

길이 한도는 토큰 수로 정하고, 한 가지 값(`CHUNK_MAX_TOKENS`)을 두 모델이 함께 쓴다. 가장 작은
후보(`multilingual-e5-base`, 512토큰)가 절단되지 않도록 `passage: `(몇 토큰)과 시작·끝 특수
토큰을 뺀 여유를 둔다. 초기값은 480이고 그룹 1의 실측 뒤에 확정한다.

- 이유: 비교에서 달라지는 변수를 모델 하나로 좁힌다. 모델마다 청크가 다르면 점수 차이가
  모델 때문인지 청크 때문인지 알 수 없다.
- 대가: `bge-m3`의 긴 입력(8192토큰)을 쓰지 못한다. 비교 결과 긴 청크가 이득이면 한도를 늘려
  다시 청크를 만든다. 청크는 `profile`로, 임베딩은 텍스트 해시로 갱신되므로 바뀐 텍스트만 다시
  계산된다.
- 두 모델이 같은 토크나이저(XLM-RoBERTa 계열)를 쓴다고 **가정**한다. 모델 카드로 확인하지
  않았다. 그룹 1에서 두 모델의 `tokenizer.json`을 비교하고, 다르면 두 토크나이저 중 큰 토큰
  수로 센다.
- 토큰 수는 주입받는 `TokenCounter`(`count(text)`와 `split_at(text, n)`)로 센다. 청크
  로직이 `tokenizers` 라이브러리 없이 단위 테스트되게 하려는 것이다.

### 2. 청크 텍스트는 이벤트마다 한 블록, 이벤트 순서 그대로

```text
[질문] source_id 설계를 어떻게 해야할것 같아?
[도구] Read(design.md)
[도구] Bash(테스트 실행) (실패)
[도구] Edit(scripts/promptlog/models.py)
[답변] 해시 대신 원문 문자열을 쓰자 ...
```

- 포함: `prompt`(`[질문]`), `answer`(`[답변]`), `tool`(`[도구]`). 제외: `thinking`, `usage`,
  `model`, `activity`, `denial`, 도구 결과 본문.
- 도구 줄은 `summarize_tool(tool_name, payload["input"])`로 만들고, 상태가 `failed`일 때만
  ` (실패)`를 붙인다. 성공은 기본이라 표시하지 않아 토큰을 아낀다.
- 대상 경로가 세션 `cwd`(`session.cwd`) 아래면 그 접두를 뗀다. 절대 경로는 토큰이 많고 사용자
  홈 경로가 모든 청크에 반복되어 임베딩에 잡음이 된다. 마스킹이 아니다(proposal Non-goals).
- 이벤트마다 블록을 만들어 이벤트 경계 분할(결정 3)이 자연스럽게 된다. 연속한 도구 호출을 한
  줄로 합치지 않는다.
- 대안 — 도구 결과의 첫 줄이나 앞부분을 넣기: 도구 결과는 본문의 대부분이고 검색 신호가
  약하다는 판단이다. 필요하면 원본 조회로 풀 수 있고(`raw_line`), 청크 규칙은 가역이다.
- 대안 — LLM으로 도구 결과 요약: 로그를 외부 API로 보내 프라이버시 결정(rag-spec §3.6)을
  깨고, 로컬 생성 모델은 이 머신에서 못 돌린다.

### 3. 분할은 이벤트 → 문단 → 토큰 순으로 내려간다

```text
턴 텍스트 <= 한도                      -> 청크 1개
턴 텍스트 >  한도                      -> 이벤트를 순서대로 담다가 넘치면 새 청크
이벤트 하나 >  한도                     -> 문단(빈 줄) 경계에서 나눔
문단 하나 >  한도                       -> 토큰 경계에서 나눔 (마지막 수단)
```

- 모든 청크가 한도 이하라는 불변식이 목적이다. 절단되는 청크가 없으면 임베딩이 청크 뒷부분을
  조용히 잃지 않는다.
- 이벤트 하나가 한도를 넘는 일은 실제로 있다. 저장소의 답변 하나가 최대 5,093자다(2026-10-06
  실측). 토큰으로는 한도를 넘을지 그룹 1에서 센다. 넘지 않아도 규칙과 테스트는 둔다.
- 두 번째 이후 청크에는 그 턴의 `[질문]` 줄을 앞 200자만 반복한다. 답변 조각만 있으면 무엇에
  대한 답인지 알 수 없어 질문과의 유사도가 떨어진다. 반복분은 한도에 포함해 센다.
- 대안 — 반복 없이 나누기, 겹치기(overlap) 두기: 겹치기는 같은 문장이 두 청크에 들어가 검색 결과가
  중복된다. 이벤트 경계에서는 문맥이 끊기지 않으므로 겹치기가 필요 없다고 본다. 이것은 가정이고
  평가에서 확인할 수 있다.

### 4. 청크 표는 파생물이고 `profile`과 턴 지문으로 갱신한다

```sql
CREATE TABLE IF NOT EXISTS chunk (
  session_key TEXT NOT NULL REFERENCES session,
  turn_no     INTEGER NOT NULL,
  part_no     INTEGER NOT NULL,
  text        TEXT NOT NULL,
  text_hash   TEXT NOT NULL,
  token_count INTEGER NOT NULL,
  ts_start    TEXT,
  ts_end      TEXT,
  tools       TEXT,          -- 사용한 도구 이름의 JSON 배열(중복 제거, 등장 순서)
  failed      INTEGER NOT NULL DEFAULT 0,
  turn_hash   TEXT,          -- 만들 때의 turn.content_hash. NULL이면 '모름'
  profile     TEXT NOT NULL, -- 청크 규칙 식별자: 형식 버전·한도·프롬프트 반복 길이
  PRIMARY KEY (session_key, turn_no, part_no)
) WITHOUT ROWID;
CREATE INDEX IF NOT EXISTS ix_chunk_hash ON chunk(text_hash);
```

- 갱신: 세션의 각 턴에 대해 `turn.content_hash`와 `profile`이 기존 청크의 `turn_hash`·`profile`과
  모두 같으면 건너뛴다. 하나라도 다르거나 `turn_hash`가 `NULL`이면 그 턴의 청크를 지우고 다시
  만든다. 색인에 더 이상 없는 턴의 청크는 지운다.
- `NULL` 지문의 턴은 매번 다시 만들어진다. 청크 텍스트 해시가 같으면 임베딩은 재사용되므로
  비용은 청킹뿐이다. 지문이 채워지면(다음 export나 `--reindex`) 건너뛰게 된다.
- 시각은 `ts_start`, `ts_end` 열에만 둔다. 텍스트에는 넣지 않는다(spec "필터용 메타데이터").
- `cwd`는 `session` 표에 이미 있어 청크에 복제하지 않고 조인으로 읽는다.
- `clear_index()`와 `--reindex`는 `chunk`를 건드리지 않는다. 재색인 뒤 `turn.content_hash`가
  같으면 청크도 그대로다.
- 대안 — 청크를 `turn`에 외래키로 묶기: 결정 5의 이유로 기각한다. 청크는 `session`만 참조한다
  (`session` 행은 지워지지 않는다).

### 5. 임베딩은 `(text_hash, model)`을 키로 저장하고 청크와 연결하지 않는다

```sql
CREATE TABLE IF NOT EXISTS embedding (
  text_hash  TEXT NOT NULL,
  model      TEXT NOT NULL,   -- '<이름>/<변형>' 예: 'bge-m3/int8'
  dim        INTEGER NOT NULL,
  vector     BLOB NOT NULL,   -- float32 little-endian, L2 정규화됨
  created_at TEXT,
  PRIMARY KEY (text_hash, model)
) WITHOUT ROWID;
```

- 임베딩은 "내용 → 벡터" 캐시다. 청크 행이 지워졌다 다시 만들어져도, 재색인을 해도, 같은
  텍스트면 벡터가 남는다. 재개 세션의 같은 텍스트는 벡터 하나를 공유한다.
- 청크가 어떤 벡터를 쓰는지는 `chunk.text_hash`로 조인한다(`embedding` 기본 키로 바로 찾는다).
- 모델 이름에 변형(int8, fp32)을 넣는 이유: 양자화에 따라 벡터가 달라지므로 같은 키에 섞이면 안
  된다.
- 텍스트가 바뀌어 더 이상 어떤 청크도 가리키지 않는 벡터(고아)는 남는다. 청크당 최대
  약 4KB(1024차원 float32)라 정리를 서두를 이유가 없고, 정리 명령은 보류한다.
- 대안 A — 턴 지문(`turn.content_hash`)을 임베딩 키로 쓰기: 도구 결과가 붙을 때마다 지문이
  바뀌는데 청크 텍스트는 안 바뀔 수 있어, 쓸데없이 다시 임베딩한다.
- 대안 B — `chunk`에 벡터 열을 두기: 청크 행이 다시 만들어질 때 벡터가 같이 날아가 결정 4의
  갱신이 임베딩 비용을 무효화한다.

### 6. 청크 갱신과 임베딩은 별도 명령에서만 돌고 의존성은 지연 임포트한다

`scripts/embed.py`(→ `promptlog/embed_cli.py`)가 두 단계를 실행한다: 청크 갱신, 벡터 없는 청크
임베딩. Stop 훅, `service.export()`, `cli.py`는 바꾸지 않는다.

- 청크 갱신에는 토크나이저가 필요하므로 훅에 넣지 않는다. 청킹 자체는 가볍지만 `tokenizers`
  임포트와 토큰 수 계산이 훅 경로를 의존성에 묶는다.
- `onnxruntime`, `tokenizers`, `numpy`, `huggingface_hub`는 함수 안에서 임포트한다. `chunk.py`는
  표준 라이브러리만 쓰고 `TokenCounter`를 주입받는다. 그래서 의존성이 없는 환경에서도 기존
  `--selftest`와 청킹 단위 테스트가 돌고, 의존성이 필요한 테스트는 `unittest.skipUnless`로 건너뛴다.
- 사용자 결정: 임베딩은 Stop 훅이 아닌 별도 명령이다. 질의 시점 자동 실행은 4단계(`ask.py`)에서
  다룬다.
- 옵션: `--model`(필수), `--variant`(기본 int8), `--output`, `--download`, `--batch`, `--chunks-only`
  (모델 없이 청크만 갱신), `--stats`(청크 수·토큰 분포·차원·표 크기 출력).

### 7. 모델은 사양 표로 정의하고 ONNX Runtime으로 직접 실행한다

```text
ModelSpec: name, repo, onnx 경로(변형별), tokenizer 경로, dim, max_tokens,
           pooling('cls' | 'mean'), query_prefix, passage_prefix
bge-m3                 cls    ''           ''
multilingual-e5-base   mean   'query: '    'passage: '
```

- 실행 순서: 접두어 붙이기 → 토크나이즈(패딩, 절단 없음) → ONNX 실행 → 마지막 은닉 상태 풀링
  (CLS는 첫 토큰, 평균은 어텐션 마스크로 가중) → L2 정규화. 풀링과 정규화는 numpy로 직접 쓴다.
  프로젝트 목적(직접 구현)과 맞고, 모델 카드로 확인한 풀링을 그대로 옮긴다.
- 모델 이름에 변형을 붙인 `model` 값(결정 5)이 `embedding.model`이 된다.
- ONNX 입력·출력 이름은 변환본마다 다를 수 있다. 입력은 세션 메타데이터로 읽고(`input_ids`,
  `attention_mask`만 넣고 `token_type_ids`는 요구될 때만), 출력은 첫 번째(`last_hidden_state`)를
  쓴다. 이것은 가정이고 그룹 4에서 변환본을 열어 확인한다.
- 검증(그룹 4): (a) 풀링·정규화 함수를 합성 텐서로 단위 테스트한다. (b) 문장 쌍으로 의미가 같은
  쌍이 다른 쌍보다 가깝다는 것을 확인한다. (c) `bge-m3`는 변환본에 풀링까지 포함한
  `sentence_transformers_*.onnx`가 있으므로(파일 목록은 확인했고 출력 형태는 미확인) 있으면 그
  출력과 직접 만든 벡터를 대조한다. (d) int8과 fp32 벡터의 코사인을 표본으로 재서 양자화 영향을
  기록한다.
- 대안 — `sentence-transformers` + torch: 코드는 한 줄이지만 설치가 1~2.5GB(rag-spec 추정)이고
  풀링·정규화가 라이브러리 뒤에 숨어 학습 목적에 맞지 않는다. ONNX 변환본이 없는 후보가 생기거나
  구현이 막히면 이 경로로 후퇴한다.
- 모델 선정 근거: `bge-m3`는 한국어 검색에서 `multilingual-e5-large`보다 높은 recall이 보고됐고
  (KURE-v1 카드: Top-1 recall 0.5178 대 0.5005), 파인튜닝판 KURE-v1이 0.5264다. 차이가 작고 이
  코퍼스에서 검증되지 않았으므로 비교로 확인한다.

### 8. 입력 한도를 넘는 텍스트는 오류로 드러낸다

임베딩 직전에 모델 자신의 토크나이저로 토큰 수를 센다. `max_tokens`를 넘으면 절단하지 않고
`InputTooLong`을 일으킨다. 청크 한도(결정 1)가 지켜지면 일어나지 않지만, 토크나이저가 다르거나
한도가 잘못 정해진 경우를 조용한 품질 저하가 아니라 오류로 만든다. 질문은 짧아 일어나지 않는다.

### 9. 계산은 트랜잭션 밖에서, 저장은 배치마다 짧게

```text
벡터 없는 (text_hash, text) 목록 조회  (읽기)
길이순 정렬 -> 배치로 나눔
  각 배치: 모델 실행 (DB 잠금 없음)  ->  INSERT OR IGNORE 후 커밋 (짧은 쓰기)
```

- 긴 계산 동안 쓰기 잠금을 쥐지 않는다. 훅의 적재(쓰기)와 겹쳐도 `busy_timeout` 안에서 끝난다.
- 배치마다 커밋하므로 중단 후 다시 실행하면 남은 것만 계산한다.
- `INSERT OR IGNORE`: 두 임베딩 명령이 동시에 돌아도 한 쪽이 다른 쪽의 행을 덮어쓰다 실패하지 않는다.
- 비슷한 길이끼리 묶으면 패딩 낭비가 줄어든다. 배치 크기 기본값은 16이고 `--batch`로 바꾼다. 최적값은
  측정하지 않았다.

### 10. 모델 파일은 명시적으로 요청할 때만 내려받는다

기본은 로컬 캐시에서만 읽는다(`huggingface_hub`의 `local_files_only`). 파일이 없으면 무엇이 없는지
알리고 `--download`를 안내하며 종료 코드 1로 끝난다. `--download`가 있을 때만 모델 파일을 받는다.

- 파일이 수백 MB라 조용히 받지 않는다.
- 내려받는 요청에는 저장소 이름과 파일 이름뿐이고 로그 텍스트는 어디에도 쓰이지 않는다. 이 성질은
  임베딩 경로에서 `socket`을 막은 상태로 실행하는 테스트로 확인한다(spec "로그 내용의 외부 전송 금지").

### 11. 모델 비교는 질문 세트와 순위 지표로, 세트는 저장소 밖에 둔다

`scripts/eval_embeddings.py`가 질문 세트를 읽어 모델마다 recall@1·3·5·10과 MRR을 출력한다.

```json
[{"question": "source_id 설계를 어떻게 정했더라", "gold": [{"session": "...", "turn": 3}]}]
```

- 순위 단위는 턴이다. 질문과 모든 청크 벡터의 점곱을 구해 같은 턴의 청크 중 최고점으로 턴 순위를
  매기고, 정답 턴 중 하나라도 상위 k에 있으면 적중이다.
- 질문 세트에는 개인 대화 내용이 들어 있으므로 저장소에 커밋하지 않는다. 기본 위치는 리포트 루트
  아래 `eval/questions.json`이다(AGENTS.md 6항).
- 정답 라벨은 사용자가 단다. `--list-turns`가 턴 번호와 프롬프트 앞부분을 보여 주어 라벨링을 돕는다.
- 한계: 질문이 20~30개면 한두 개 차이는 잡음이다. 비율만 말하지 않고 적중 개수를 함께 기록하고,
  차이가 한두 개면 우열을 가리지 않는다. 질문이 청크 내용 단어를 그대로 쓰면 어휘 일치가 점수를 올리므로
  의미만으로 묻는 질문을 섞도록 안내한다.
- 비교용 점곱 순위는 `vectors.py`에 작게 두고, 3단계 `search.py`가 필요하면 가져다 쓴다.

### 12. 스키마 버전 3

`SCHEMA`에 두 표와 인덱스를 추가하고, `MIGRATIONS[2]`가 같은 `CREATE ... IF NOT EXISTS` 문을 실행한다.
`TABLES` 상수에 `chunk`, `embedding`을 더한다. 업그레이드 경로(`BEGIN IMMEDIATE`, 버전 재확인, 롤백)는
1단계 그대로다. 기존 테스트 중 버전을 2로 고정한 단언이 있어 `SCHEMA_VERSION`으로 바꿔야 한다.

## Risks / Trade-offs

- **[두 모델의 토크나이저가 같다는 가정이 틀린다]** 청크 한도가 한쪽에서 어긋나 절단되거나 임베딩이
  `InputTooLong`으로 실패한다. → 그룹 1에서 비교하고, 다르면 큰 쪽 토큰 수로 센다. 결정 8이 조용한
  절단 대신 오류로 드러낸다.
- **[ONNX 변환본의 입출력이 가정과 다르다]** → 그룹 4에서 변환본을 열어 확인한다. 풀링 오류는 이웃
  문장이 오히려 멀어지는 등 의미 점검에서 드러난다.
- **[int8 양자화가 벡터를 바꿔 검색 품질이 떨어진다]** 영향은 재 보지 않았다. → 표본으로 fp32와
  코사인을 재서 기록하고, 크면 변형을 fp16이나 fp32로 바꾼다. 모델 이름에 변형이 들어 있어 공존한다.
- **[CPU 임베딩이 예상보다 오래 걸린다]** 4코어 CPU에서 속도는 측정하지 않았다. 코퍼스가 수천 청크라고
  가정하면 분 단위에서 수십 분일 것으로 짐작한다(추정). → 별도 명령에 배치별 진행 출력과 중단·재개를
  넣었다. 그룹 5에서 실측해 기록한다.
- **[평가 질문이 적어 비교가 잡음에 묻힌다]** → 적중 개수를 기록하고 차이가 작으면 우열을 가리지
  않는다(결정 11).
- **[청크에 홈 경로나 키가 섞인다]** 프롬프트와 답변에는 사용자가 붙여 넣은 값이 있을 수 있고 경로는
  `cwd` 밖에서는 그대로 남는다. → 임베딩은 로컬에서만 일어나고 저장소 파일 권한은 0600이다. 검색 조각이
  외부로 나가기 전의 마스킹은 3~4단계가 정한다.
- **[재개 세션의 같은 턴이 청크로 두 벌 생긴다]** 두 세션이 같은 이벤트를 공유하면 같은 텍스트 청크가
  세션마다 하나씩 있다. 임베딩은 텍스트 해시로 공유되지만 검색 결과는 중복될 수 있다. → 3단계가
  텍스트 해시로 합친다.
- **[고아 임베딩이 쌓인다]** 청크 텍스트가 바뀌면 이전 벡터가 남는다. → 청크당 약 4KB라 당장은 문제가
  아니고, 정리 명령은 보류한다.
- **[`onnxruntime`·`tokenizers`의 Windows·Python 3.11 휠이 있다고 가정했다]** 확인하지 않았다. → 그룹 1에서
  설치해 확인한다.

## Migration Plan

1. 새 코드가 처음 저장소에 연결할 때 버전 2 → 3으로 자동 업그레이드한다. 표만 추가하므로 기존 행은 바뀌지
   않는다.
2. 임베딩은 선택이다. 의존성을 설치하지 않으면 지금처럼 동작한다. 사용하려면 의존성을 설치하고
   `python -B scripts/embed.py --model bge-m3 --download`를 한 번 실행한다.
3. 롤백은 `export()`에서 달라지는 것이 없으므로 코드 되돌리기로 충분하지만, 버전 3 저장소는 이전
   코드가 거부한다. 필요하면 `DROP TABLE chunk; DROP TABLE embedding; PRAGMA user_version = 2;`를 실행한다.
   두 표는 모두 재생성되는 파생물이다.
