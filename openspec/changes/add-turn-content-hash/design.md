# Design

## Context

동기는 [proposal.md](proposal.md) Why를 본다. 설계를 제약하는 현재 상태는 넷이다.

1. `write_index()`는 export와 `--reindex` 양쪽에서 세션의 `turn` 행을 지우고 다시
   쓴다(`store.py`). 턴 번호는 `assign_turns()`가 프롬프트 개수로만 매기므로, 같은 원본에서는
   항상 같은 번호가 나온다.
2. `ensure_schema()`는 `executescript(SCHEMA)`로 스키마를 적용한다. 모든 문이
   `CREATE ... IF NOT EXISTS`라서 이미 있는 테이블에는 아무 일도 하지 않는다. 그래서
   기존 `turn`에 컬럼을 더하려면 별도의 업그레이드 경로가 필요하다.
3. Python `sqlite3`의 `executescript()`는 실행 전에 열린 트랜잭션을 커밋하고, 기본
   트랜잭션 제어는 DDL 앞에서 암묵적으로 `BEGIN`하지 않는다(Python 3.11 `sqlite3`
   문서, `isolation_level`). 그래서 업그레이드를 원자적으로 하려면 트랜잭션을 명시해야 한다.
4. Stop 훅은 병렬로 돌 수 있다(`add-raw-log-store` design 결정 8). 버전 1 저장소를 두
   프로세스가 동시에 열면 업그레이드가 경합한다.

## Goals / Non-Goals

**Goals:**

- 지문은 이미 색인에 들어가는 값만으로 계산한다. 새 파싱 규칙이나 추가 조회 없이
  `write_index()` 안에서 끝낸다.
- 업그레이드는 동시에 열려도 한 번만 일어나고, 실패하면 버전 1 그대로 남는다.

**Non-Goals:**

- 지문을 소비하는 쪽(임베딩 표, "바뀐 턴" 조회 함수). 2단계에서 소비 방식과 함께 정한다.
- 일반적인 마이그레이션 프레임워크. 버전 1 → 2 하나만 다루되, 단계가 늘어날 때 같은
  모양으로 이어 붙일 수 있게만 둔다.

## Decisions

### 1. 지문 = 턴에 속한 이벤트의 색인 행을 순서대로 직렬화한 SHA-256

`event_row()`가 만드는 값 `(source_id, kind, ts, text, tool_name, status, payload)`를
턴 안의 이벤트 순서대로 JSON 배열로 직렬화해 `sha256` 16진 문자열(64자)로 만든다.

- `seq`와 `turn_no`는 넣지 않는다. `seq`는 앞쪽에 이벤트 하나가 끼어들면 뒤의 모든
  값이 밀리므로(proposal Why), 넣으면 모든 턴의 지문이 함께 바뀐다.
- 대안 A — 갱신 시각이나 버전 카운터: 재색인할 때마다 모든 턴이 "바뀜"이 되어 재색인이
  2단계 임베딩을 전부 무효화한다. 결정적이지 않아서 기각한다.
- 대안 B — 턴에 해당하는 원본 줄의 해시: 턴은 파싱 이후의 개념이라 원본 줄과 1:1로
  대응하지 않는다. 다음 줄의 도구 결과가 이전 턴의 이벤트를 바꾸는 경우도 잡지 못한다.
- 대안 C — 2단계 청크 텍스트의 해시: 청킹 규칙이 아직 없다. 턴 지문은 색인 내용
  기준으로 두고, 청킹 규칙 버전은 2단계 임베딩 키가 따로 가진다.
- 잘라 쓰지 않는다. 64자 문자열은 턴 수만큼만 생기고 충돌 가능성을 따질 이유가 없다.

### 2. 이벤트 행은 한 번만 만든다

`write_index()`가 `event` 적재용으로 이미 `event_row()`를 이벤트마다 부른다. 지문도 같은
행으로 계산하도록 `turn_rows()`에 그 행 목록을 넘긴다. 같은 `json.dumps`를 두 번 하지
않으려는 것이고, `event` 표에 쓴 값과 지문의 입력이 같다는 사실을 코드 구조로 보장하려는
것이기도 하다.

### 3. 업그레이드는 버전별 문 목록 + `BEGIN IMMEDIATE` 안에서 버전 재확인

```text
MIGRATIONS = {1: ("ALTER TABLE turn ADD COLUMN content_hash TEXT",)}

ensure_schema
  version == 0 (새 파일)   -> SCHEMA(최신 정의) 적용, user_version = 최신
  0 < version < 최신       -> BEGIN IMMEDIATE
                              -> user_version 다시 읽기 (다른 프로세스가 먼저 올렸으면 그대로 종료)
                              -> version부터 최신-1까지 MIGRATIONS 실행
                              -> user_version = 최신 -> COMMIT  (오류 시 ROLLBACK)
  version > 최신           -> 변경 없이 거부 (기존 동작)
```

- `BEGIN IMMEDIATE`는 시작할 때 쓰기 잠금을 잡는다. 두 번째 프로세스는 `busy_timeout`
  동안 기다렸다가 잠금을 얻은 뒤 버전을 다시 읽고 이미 최신임을 확인한다. 재확인이 없으면
  두 번째 프로세스의 `ALTER`가 `duplicate column name`으로 실패한다.
- `ALTER TABLE ... ADD COLUMN`과 `PRAGMA user_version` 쓰기는 같은 트랜잭션에
  묶이므로, 중간에 실패하면 둘 다 되돌아간다. 이 성질은 실패 주입 테스트로 확인한다.
- 버전별 문을 데이터(`MIGRATIONS`)로 두는 이유는 테스트에서 실패할 문을 끼워 넣어
  롤백을 검증할 수 있게 하기 위해서다.
- 대안 — 테이블을 새로 만들어 복사: 컬럼 하나 추가에 비해 과하고, 복사 중 실패 처리가
  더 복잡하다.
- 대안 — 업그레이드 때 지문까지 계산: 지문은 파싱 결과가 있어야 계산되는데 저장소는
  어댑터를 모른다(`add-raw-log-store` 6.1의 분리). 그래서 업그레이드는 컬럼만 더한다.

### 4. 업그레이드 직후 지문은 `NULL`

기존 턴의 `content_hash`는 `NULL`로 남는다. 계산된 지문과 구분되는 빈 값이며
(log-index 스펙 "아직 계산되지 않은 지문은 구분된다"), 두 경로가 채운다.

- 그 세션의 다음 export. `write_index()`가 세션의 `turn` 행을 다시 쓰기 때문이다.
- `--reindex`. 모든 세션을 다시 쓴다.

실제 저장소는 지금 세션 6개라 `--reindex` 한 번이면 끝난다. 2단계 소비자는 `NULL`을
"아직 모름"으로 다루고 처리 대상에서 빼거나 재색인을 안내하면 된다.

## Risks / Trade-offs

- **[재개 세션 공유 이벤트의 내용 불일치]** 공유 이벤트 중 0.3%는 세션마다 본문이 다르고,
  `event` 행은 마지막 적재가 이긴다(`add-raw-log-store` design Risks). 지문은 각 세션이
  자신의 파싱 결과로 계산하므로, 다른 세션의 적재로 `event` 행 내용이 바뀌어도 이 세션의
  턴 지문은 바뀌지 않는다. → 2단계에서 청크 텍스트를 `event` 표에서 만들지, 세션별 파싱
  결과에서 만들지 정할 때 함께 다룬다 (Open Questions).
- **[`Event`에 필드가 추가되면 모든 지문이 바뀐다]** `payload`가 `Event`의 나머지
  필드를 담기 때문이다. → 의도된 동작이다. 색인 내용이 실제로 바뀌므로 다시 처리하는 게
  맞다. 2단계 재임베딩 비용이 한 번 든다.
- **[이전 코드로 되돌리면 버전 2 저장소를 못 연다]** 기존의 "더 새로운 버전 거부"에
  걸린다. export에서는 `archive()`가 오류를 삼키므로 리포트 생성은 계속된다. →
  되돌릴 일이 생기면 `content_hash` 컬럼을 무시하는 것으로 충분하지만, SQLite에서
  `user_version`을 내리는 것은 수동 작업이다. 이번 범위에서는 대비하지 않는다.
- **[export마다 해시 계산 비용]** 이벤트 행 직렬화는 이미 하고 있으므로 추가 비용은
  SHA-256 한 번이다. → 9.0MB 실제 세션으로 전후 시간을 재서 기록한다 (tasks 3).

## Migration Plan

1. 새 코드가 처음 저장소에 연결할 때 버전 1 → 2로 자동 업그레이드한다. Stop 훅이 첫
   연결이어도 같은 경로를 탄다.
2. 업그레이드 후 `python -B scripts/export.py --reindex`를 한 번 실행해 기존 턴의 지문을
   채운다. 실행하지 않아도 활성 세션은 다음 export 때 채워진다.
3. 롤백은 코드만 되돌려서는 안 된다(위 Risks). 필요하면 `--reindex`로 다시 만들 수 있는
   색인이므로, 저장소를 지우는 대신 `user_version`을 1로 내리고 컬럼을 무시하면 된다.

## Open Questions

- 2단계 청크 텍스트의 출처(`event` 표 대 세션별 파싱 결과). 지문 계산 방식이나 이번
  태스크에는 영향이 없고, 2단계 설계에서 정한다.

## 보류된 개선

구현 중 발견했지만 멈출 기준에 해당하지 않아 미룬 문제를 여기 기록한다. 항목 형식:
무엇 / 왜 미뤘나 / 고칠 방향 / 발견 시점.

### 1. 새 저장소 파일을 두 연결이 동시에 처음 열면 WAL 전환이 잠금 오류로 실패할 수 있다

- **무엇**: `connect()`는 연결마다 `PRAGMA journal_mode = WAL`을 실행한다. 파일이 아직
  rollback-journal 모드일 때 두 연결이 동시에 전환하면, 한쪽이 `busy_timeout`(5초)을
  기다리지 않고 2ms 만에 `database is locked`로 실패했다(합성 재현 5회 중 1회). 기다리지
  않는 이유는 SQLite가 이 잠금 상승 경로에서 교착을 피하려 busy handler를 부르지 않기
  때문으로 보인다(추정, 근거 미확인).
- **왜 미뤘나**: 이번 변경 이전부터 있던 동작이다. WAL은 파일에 영구 기록되므로 실제로는
  저장소 파일을 처음 만드는 순간에만 일어날 수 있다. 실제 저장소는 이미 WAL이다(파일 헤더
  18·19바이트 = 2). 일어나더라도 `archive()`가 오류를 삼켜 리포트는 생성되고, 다음 턴의
  증분 적재가 같은 줄을 다시 읽으므로 원본은 유실되지 않는다.
- **고칠 방향**: 이미 WAL이면 전환을 건너뛰거나(`PRAGMA journal_mode` 조회 후 분기), 전환
  실패를 짧게 재시도한다. 처음 생성 경합을 재현하는 테스트를 함께 둔다.
- **발견**: 그룹 1 구현 중. 업그레이드 동시성 테스트의 v1 픽스처를 rollback-journal로
  만들었을 때 드러났다. 실제 v1 저장소와 같도록 픽스처를 WAL로 바꿔 업그레이드 경합만
  검증하게 했다.

### 2. `write_index()`가 31줄이다

- **무엇**: AGENTS.md의 함수 30줄 제한을 1줄 넘는다. `add-raw-log-store` 그룹 6 수정에서
  생긴 것이다.
- **왜 미뤘나**: 그룹 1 범위 밖이고, 그룹 2.1이 이 함수를 바로 고친다.
- **고칠 방향**: 2.1에서 이벤트 행을 한 번 만들어 넘길 때 SQL 묶음을 나눠 30줄 이하로 맞춘다.
- **발견**: 그룹 1 검증 중 (함수 길이 검사)
